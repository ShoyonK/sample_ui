## 1. APPLICATION LAUNCH & INITIALIZATION

### USER REQUIREMENTS
- User can launch SiRAT from PyCharm debug console while paused at breakpoint
- User can launch SiRAT in blocking mode (waits for window close)
- User can launch SiRAT in non-blocking async mode (returns immediately)
- User can launch SiRAT from Python code within test context
- User can close SiRAT via window controls or Ctrl+Q

### FUNCTIONAL REQUIREMENTS

**Workspace Root Detection:**
- Method 1: Inspect `dut.configurators.phy` module path, navigate up 7 directory levels
- Method 2: Search upward from current working directory looking for workspace markers:
  - `tests/series_six` directory exists
  - `configs/station_configurations` directory exists
- Method 3: Fallback to current working directory
- Log warning if workspace root cannot be determined

**DUT Validation:**
- Parent object must have `.dut` attribute OR parent itself must be DUT
- DUT must have `.rm` register map with `readByName()` and `writeByName()` methods
- No explicit validation - fails at runtime if requirements not met

**Initialization Sequence:**
1. Setup logging with console and file handlers
2. Create/reuse QApplication singleton instance
3. Set application name to 'SiRAT'
4. Load window icon from `SiRAT_logo.png` if exists
5. Create session debug log file: `C:/temp/sirat/session_log_<timestamp>.log`
6. Initialize core models: AccessPolicy, DutInterface, SvdLoader, SessionData, FieldCalculation, FieldNotes
7. Setup disconnect detection callback on DutInterface
8. Load peripherals from DUT register map (filters `_NS/_S` by default)
9. Create main window UI components
10. Load persistent user settings from `~/.sirat/` directory
11. Show window maximized
12. Start Qt event loop (blocking or background thread based on launch mode)

**Auto-Load on Startup:**
- Favorites from `~/.sirat_favorites.json`
- Actions from `~/.sirat_actions.json`
- Watch list from `~/.sirat_watch_list.json`
- Data logger config from `~/.sirat_data_logger.json`
- Custom functions from `~/.sirat_custom_functions.json`
- Sequences from `~/.sirat_sequences.json`
- Field formulas from `~/.sirat/field_formulas.json`
- Field notes from `~/.sirat/field_notes.json`
- Preferences from `~/.sirat/preferences.json`

**Singleton Behavior:**
- Multiple calls to launch functions bring existing window to front instead of creating duplicate
- QApplication reused if already exists

### UI REQUIREMENTS

**Window Properties:**
- Title: "SiRAT"
- Size: 1400x900 pixels
- Position: (100, 100) on screen
- Icon: `SiRAT_logo.png` from package directory
- Initial state: Maximized
- Window flags: Standard main window

**Launch Indicators:**
- No splash screen
- Window appears immediately after initialization
- Loading happens in background with lazy evaluation

### DATA REQUIREMENTS

**Session Debug Log:**
- Location: `C:/temp/sirat/session_log_<YYYYMMDD_HHMMSS>.log`
- Format: Plain text with timestamps
- Pattern: `<timestamp> - <level> - <logger_name> - <message>`
- Encoding: UTF-8
- Retention: Manual cleanup (not auto-deleted)

**Python Dependencies:**
```
PyQt5>=5.15.0          # GUI framework
pyqtgraph>=0.13.0      # Plotting
```

**Python Version:**
- Required: Python 3.10 (workspace standard)
- No explicit version check in code

**Entry Points:**
```python
# From __init__.py
launch_viewer(parent, log_level=logging.INFO) -> int
launch_viewer_async(parent, log_level=logging.INFO) -> ViewerHandle
```

**Version:**
- Current: "0.1.0" (from `_version.py`)

## 3. DUT CONNECTION MANAGEMENT

### USER REQUIREMENTS
- User can connect to DUT via menu action "Connect to DUT"
- User can specify DUT position (1-4)
- User can select DUT config type (EFX, EFR32)
- User can optionally specify custom DUT config file path
- User sees connection progress in real-time
- User can reconnect RPC if connection lost
- User can add reconnect operation to Actions
- User sees disconnect recovery dialog when DUT disconnects

### FUNCTIONAL REQUIREMENTS

**Connection Process:**
1. User opens DUT Connect Dialog
2. User selects DUT position (1-4), config type, optional config file
3. User clicks "Connect" button
4. Background thread started (non-blocking UI)
5. Calls `BenchUtils.connect_six_dut_rf(position, config_type, config_file)`
6. Establishes RPC connection via `dut.rpc_io.Connect()`
7. Finds Session object from `dut.Session` or `SessionGlobals.Session`
8. Stores DUT and Session references in parent object
9. Updates console with success message or error traceback
10. Re-enables Connect button

**Disconnect Detection:**
- DutInterface monitors all read/write operations
- Checks error messages for disconnect indicators:
  - 'Disconnected'
  - 'Cannot read register'
  - 'Cannot write register'
  - 'is not accessible'
  - 'RPC connection lost'
  - 'Connection timeout'
- If disconnect detected and callback registered:
  - Calls `main_window._on_dut_disconnect()`
  - Debounces: Ignores disconnects within 2 seconds of previous
  - Shows DisconnectRecoveryDialog (only if not already shown)

**Disconnect Recovery Flow:**
1. Modal DisconnectRecoveryDialog appears
2. User clicks "Reconnect" button
3. Calls `dut.rpc_io.Connect()`
4. On success:
   - Shows success message
   - Enables "Load LPW PHY" and "Load WiFi PHY" buttons
   - Shows PHY instruction panel
5. User loads PHY as needed
6. User closes dialog

**Reconnect Operation:**
- Creates `dut_reconnect` operation type
- Can be added to Actions for automated reconnection
- Operation format:
```python
{
    'type': 'dut_reconnect',
    'description': 'Reconnect RPC'
}
```

### UI REQUIREMENTS

**DUT Connect Dialog:**
- Window: Non-modal, independent, 700x600 pixels
- Title: "Connect to DUT"
- Layout:
  - DUT Position dropdown (1, 2, 3, 4)
  - DUT Config Type dropdown (EFX, EFR32)
  - DUT Config File text input (placeholder: "Leave empty for station default")
  - Console output (QTextEdit, read-only, Courier 10pt)
  - Button row: Connect, Close
- Button states:
  - Connect: Enabled initially, disabled during connection ("⏳ Connecting...")
  - Close: Always enabled

**Disconnect Recovery Dialog:**
- Window: Modal dialog, 600x400 pixels
- Title: "DUT Disconnected"
- Icon: Warning icon (❗)
- Layout:
  - Header: "⚠️ DUT Connection Lost" (bold, red, 14pt)
  - Explanation text: Common causes (power cycle, J-Link disconnect, firmware assert)
  - Status message label (green for success, red for error)
  - PHY instruction panel (shown after successful reconnect)
  - Button row: Reconnect, Load LPW PHY, Load WiFi PHY, Close
- Button states:
  - Reconnect: Changes text during operation ("Reconnecting..." → "✓ Connected")
  - PHY buttons: Disabled until reconnect succeeds, then enabled
  - Close: Always enabled

**Console Output Colors:**
- Success: Green (100, 255, 100)
- Error: Red (255, 100, 100)
- Warning: Orange (255, 200, 100)
- Info: Blue (100, 200, 255)
- Default: White text on black background

### DATA REQUIREMENTS

**Connection State:**
- Stored in parent object attributes:
  - `parent.dut` - DUT instance
  - `parent.Session` - Session object (if found)
- Not persisted to disk
- Lost when SiRAT closes

**Disconnect Debounce:**
```python
_last_disconnect_time: float = 0  # Timestamp of last disconnect
_disconnect_dialog_shown: bool = False  # Prevent multiple dialogs
```

**Reconnect Action Data:**
```json
{
    "type": "dut_reconnect",
    "description": "Reconnect RPC"
}
```

## 4. PERIPHERAL TREE VIEW

### USER REQUIREMENTS
- User can browse hierarchical list of peripherals and registers
- User can expand/collapse peripherals to see registers
- User can search/filter peripherals and registers by name
- User can click peripheral to see information
- User can click register to select and optionally auto-read it
- User can right-click peripheral to read all registers
- User can collapse entire tree with "Collapse All" button
- User sees register values update after reads
- User sees color-coded registers based on access type

### FUNCTIONAL REQUIREMENTS

**Peripheral Loading:**
- Peripherals loaded from `SvdLoader.load_peripherals(dut.rm)`
- Filters peripherals by default: hides those with `_NS` or `_S` in name
- User can toggle filter via menu: "Show Peripherals with _NS/_S"
- Filter state saved to preferences
- Peripherals sorted alphabetically by name

**Lazy Loading of Registers:**
- Peripherals initially created with placeholder child "Loading..."
- On first expansion: Removes placeholder, creates register child items
- Prevents loading ~300 registers for 100+ peripherals upfront
- Performance optimization for large register maps

**Search & Filter:**
- Real-time filtering with 300ms debounce
- Matches against:
  - Peripheral names
  - Register names
  - Field names (by examining register.fields)
- Search behavior:
  - Match by peripheral: Shows all registers in peripheral, expands peripheral
  - Match by register: Shows only matching registers, expands parent peripheral
  - Match by field: Shows registers containing matching field
  - Empty search: Collapses all, shows all items
- Auto-selects register if exactly one match found
- Search box has clear button (X)

**Item Selection:**
- Single-click peripheral: Emits `peripheral_selected(PeripheralModel)`, expands if has registers
- Single-click register: Emits two signals:
  - `register_selected(RegisterModel)` - UI update only
  - `register_selected_by_user(RegisterModel)` - Triggers auto-read if enabled
- Distinction allows DetailView to update without triggering auto-read

**Context Menu:**
- Right-click on peripheral: Shows "Read All Registers" option
- Executes: Reads all registers sequentially with progress dialog
- Updates tree values and DetailView cache
- Shows completion message: "{peripheral.name}: X registers read, Y failed"

**Value Updates:**
- Initial state: Register value column shows "─" (not read yet)
- After read: Shows formatted value (hex/dec/bin based on format setting)
- Updated via `update_register_value(register, value)` called from main window
- Uses `_register_items` dict for O(1) lookup by full_name

### UI REQUIREMENTS

**Tree Structure:**
- QTreeWidget with 3 columns: Name | Address | Value
- Column widths: [200, 100, auto] (Name, Address, Value stretch)
- Single selection mode
- Alternating row colors: Enabled
- Font: 11pt default
- Icons: 📦 for peripherals, 📄 for registers

**Search Box:**
- QLineEdit with placeholder: "Filter peripherals/registers..."
- Clear button (X) on right side
- Located above tree
- Font: 11pt

**Collapse All Button:**
- Text: "🗁 Collapse All"
- Maximum width: 120px
- Located below tree
- Style: Default button style

**Color Coding:**
- Register row background colored by `access_policy.get_access_color(register.access)`:
  - Read-only: Light blue (#E3F2FD)
  - Read-write: Light green (#E8F5E9)
  - Write-only: Light red (#FFEBEE)
  - Write-once: Light orange (#FFF3E0)
  - Read-write-once: Light purple (#F3E5F5)
  - Unknown: Light gray (#F5F5F5)

**Address Format:**
- Hex format: `0x<address in 8-digit uppercase hex>`
- Example: `0x40084000`

**Value Format:**
- Not read: "─"
- After read: Formatted per user preference (hex/dec/bin)
- Default: Hex format `0x<value in 8-digit uppercase hex>`

**Progress Dialog (Read All):**
- Modal dialog
- Cancelable
- Title: "Reading Registers"
- Label updates per register: "Reading {peripheral}.{register}..."
- Shows progress: X of Y registers

### DATA REQUIREMENTS

**Tree Item Storage:**
```python
# Item.data(Qt.UserRole) stores tuple:
('peripheral', PeripheralModel)  # For peripheral items
('register', RegisterModel)      # For register items
('placeholder', None)            # For lazy-load placeholder
```

**Value Cache:**
```python
_register_items: Dict[str, QTreeWidgetItem]
# Maps full_name -> QTreeWidgetItem for O(1) updates
```

**Search State:**
```python
_search_timer: QTimer  # Single-shot, 300ms timeout
_pending_search_text: str  # Buffered search text
```

**No Persistence:**
- Tree expansion state not saved
- Search text not saved
- Scroll position not saved

## 5. REGISTER DETAIL VIEW

### USER REQUIREMENTS
- User can view detailed information about selected register
- User can read register value from hardware
- User can write register value to hardware
- User can toggle individual bits via interactive bit pattern widget
- User can view and edit field values in table
- User can add/remove register from favorites
- User can add fields to data logger
- User can add fields to watch list
- User can define formulas for calculated values
- User can add notes to fields
- User can save current register state to actions
- User can choose display format (Hex/Dec/Bin)
- User can auto-write field values by pressing Enter in table

### FUNCTIONAL REQUIREMENTS

**Display Modes:**
- **Register Mode**: Shows single register with fields, value, bit pattern
- **Peripheral Mode**: Shows peripheral info with "Read All Registers" button
- Mode determined by what's passed to `show_register()` vs `show_peripheral()`

**Read Operation:**
1. User clicks "Read Register" button
2. Calls `dut_interface.read_register(register)`
3. Updates register value display
4. Extracts and displays all field values
5. Updates bit pattern widget
6. Stores value in cache: `_read_register_values[full_name] = value`
7. Updates `session_data.last_values[full_name]` for change detection
8. Emits `register_read(register, value)` signal
9. Logs operation to history panel (only manual reads, not auto-reads)

**Write Operation:**
1. User edits register value in text box
2. User clicks "Write Register" button
3. Parses value string (hex, dec, or bin format)
4. Shows confirmation dialog if `access_policy.requires_confirmation(peripheral_name)` is True
5. Calls `dut_interface.write_register(register, value)`
6. Reads back register for verification
7. If read-back ≠ written value: Shows warning dialog with details
8. Updates all displays with read-back value (not written value)
9. Updates cache and last_values
10. Logs operation to history panel

**Field-Level Write (Auto-Write):**
1. User double-clicks Value cell to edit
2. User types new value and presses Enter
3. Validates value is within field's bit width: `0 <= value <= (2^bit_width - 1)`
4. Shows confirmation dialog if required by AccessPolicy
5. Reads current register value
6. Inserts new field value using `field.insert_value(current, new_value)`
7. Writes modified register value
8. Reads back entire register
9. Updates all field displays with read-back values
10. Logs as field write to history panel with full register value

**Bit Toggle Instant Write:**
1. User clicks bit in BitToggleWidget
2. Widget emits `value_changed(new_register_value)` signal
3. Connected to `_on_bit_toggle_changed(value)` slot
4. Shows confirmation dialog if required
5. If user confirms or no confirmation needed:
   - Writes new value via `dut_interface.write_register()`
   - Reads back and updates displays
6. If user cancels:
   - Reverts BitToggleWidget to previous value (no write)

**Change Detection:**
- Compares current field value to `session_data.last_values[register.full_name]`
- Extracts old field value using `field.extract_value(old_register_value)`
- If old_field_value ≠ current_field_value:
  - Highlights field row with yellow background
  - Sets tooltip: "Value changed: was 0xX, now 0xY"

**Enum Display:**
- For fields with enumerations: Calls `field.get_enum_by_value(field_value)`
- If enum found: Displays enum name in Enum column, dark green color
- Tooltip: "{enum.name} ({value})\n{description}"

**Calculated Values:**
- For each field: Checks `field_calculator.has_formula(field.full_name)`
- If formula exists: Calls `field_calculator.format_result(field.full_name, field_value)`
- Displays result in Calculated column with blue text
- Column hidden if no fields have formulas

**Field Notes:**
- Notes column always visible and editable
- On edit: Calls `field_notes.set_note(field.full_name, note_text)`
- If note exists: Light yellow background
- Auto-saved on change (no explicit save button)

**Favorites:**
- Star button visible only for registers (hidden for peripherals)
- Click star: Toggles `session_data.add_favorite()` / `remove_favorite()`
- Emits `favorites_changed()` signal
- Button icon updates: ⭐ (favorited) ☆ (not favorited)

**Formula Management:**
- Formula button per field
- Click opens `FieldFormulaDialog(field.full_name, current_formula)`
- User enters Python expression using 'x' as variable
- User enters unit (Hz, MHz, V, etc.)
- On save: Calls `field_calculator.set_formula(field.full_name, formula, unit)`
- Updates Calculated column display

**Save to Actions:**
- Button: "💾 Save Register to Actions"
- Prompt for action name
- Creates register set with all current field values
- Adds to actions panel

### UI REQUIREMENTS

**Layout:**
```
RegisterDetailView
├── Register Information Group
│   └── Name + Star Button + Chip Info
├── Register Value Group
│   └── Value Edit | Format Combo | Read Button | Write Button
├── Bit Pattern Group
│   └── BitToggleWidget (32 interactive checkboxes)
└── Bit Fields Group

```

**Register Information:**
- Name label: Bold, 14pt
- Star button: Max 40px width, ⭐/☆ icon
- Chip info label: Bold, 28pt, right-aligned, shows "FAMILY revX"
- Address: Format `0x<8-digit hex uppercase>`

**Register Value:**
- Value edit: Stretch=3, placeholder "0x00000000"
- Format combo: Options [Hex, Dec, Bin], default Hex
- Read button: Standard QPushButton
- Write button: Standard QPushButton
- Not-read-yet state: Shows `<not read yet - click "Read Register">`

**Bit Pattern Widget:**
- 32 bits arranged in 4 byte groups: [31..24] [23..16] [15..8] [7..0]
- Each bit: 28x28px checkbox, toggleable
- Bit number labels below each bit
- Byte group labels above: "Byte 3", "Byte 2", "Byte 1", "Byte 0"

- Bit colors:
  - Set (1): Light green background (#90EE90), forest green border (#228B22)
  - Cleared (0): Light gray background (#E0E0E0), gray border (#999)

**Fields Table:**
- 11 columns: Bits | Name | Access | Value | Enum | Calculated | Description | Watch | Logger | Formula | Notes
- Column widths:
  - Bits: ResizeToContents
  - Name: 120px, Interactive (user-resizable)
  - Access: ResizeToContents
  - Value: 80px, Interactive

  - Logger: 50px, Fixed

  - Notes: Stretch
- Alternating row colors: Enabled

**Field Table Cell Styling:**

### FUNCTIONAL REQUIREMENTS

**Search Execution:**
- Debounced with 300ms delay after last keystroke
- Implemented with QTimer single-shot
- On timer timeout: Calls `_perform_search()`
- Disables tree updates during search, re-enables after (performance)

**Matching Algorithm:**
1. Convert search text to lowercase
2. For each peripheral:
   - Match peripheral name (case-insensitive substring)
   - If peripheral matches: Show all registers, expand peripheral
3. For each register (if peripheral didn't match):
   - Match register name (case-insensitive substring)
   - If register matches: Show register, expand parent peripheral
4. For each field in register (if register didn't match):
   - Match field name (case-insensitive substring)
   - If field matches: Show register, expand parent peripheral
5. Hide all non-matching items
6. If exactly 1 register matches: Auto-select and emit `register_selected`

**Empty Search Behavior:**
- Shows all peripherals
- Hides all registers (collapsed state)
- Clears selection

**Filter State:**
- "_NS/_S Filter" stored separately from search
- Applied in addition to search filter
- Controlled via menu checkbox

**Visual Feedback:**
- Matched items: Visible and expanded
- Non-matched items: Hidden (not grayed out)

**Debounce Indicator:**

## 7. ACCESS POLICY & SAFETY

### USER REQUIREMENTS
- User prevented from reading write-only fields
- User prevented from writing read-only fields
- User warned before writing to critical peripherals (CMU, EMU, MSC, SMU)
- User sees visual indicators of access permissions
- User can disable confirmation dialogs via settings
- User sees color-coding of registers/fields by access type

### FUNCTIONAL REQUIREMENTS

**Access Types (from CMSIS-SVD):**
- `read-only` → READ_ONLY
- `write-only` → WRITE_ONLY
- `read-write` → READ_WRITE
- `writeOnce` → WRITE_ONCE
- `read-writeOnce` → READ_WRITE_ONCE
- Unknown strings → UNKNOWN

**Read Permission Check:**
- Allowed: READ_ONLY, READ_WRITE, READ_WRITE_ONCE
- Blocked: WRITE_ONLY, WRITE_ONCE, UNKNOWN
- On attempt to read write-only:
  - Logs warning: "Cannot read write-only field: {full_name}"
  - Returns None (no read attempt)

**Write Permission Check:**
- Allowed: WRITE_ONLY, READ_WRITE, WRITE_ONCE, READ_WRITE_ONCE
- Blocked: READ_ONLY, UNKNOWN
- On attempt to write read-only:
  - Logs warning: "Cannot write read-only field: {full_name}"
  - Returns False (no write attempt)

**Value Range Validation:**
- Before write: Checks `0 <= value <= (2^bit_width - 1)`
- On out-of-range:
  - Logs error: "Value 0xX out of range for {full_name} (max: 0xY)"
  - Returns False (no write attempt)

**Critical Peripheral Confirmation:**
- Critical peripherals: CMU, EMU, MSC, SMU
- On write to critical peripheral:
  - If `confirmation_disabled` is False: Shows confirmation dialog
  - If user cancels: Aborts write
  - If user checks "Don't show again": Sets `confirmation_disabled = True`
- Confirmation can be re-enabled via Settings menu

**Read-Sensitive Peripherals:**
- Peripherals with side effects: USART, I2C, SPI
- Reading these clears FIFOs/flags
- No blocking, just informational logging

**Write Verification:**
- After every write: Reads back register value
- If read-back ≠ written value:
  - Shows warning dialog with written vs read-back
  - Possible causes: Read-only bits, hardware override
  - Uses read-back value for display (not written value)

### UI REQUIREMENTS

**Access Type Colors:**
- READ_ONLY: #E3F2FD (light blue)
- READ_WRITE: #E8F5E9 (light green)
- WRITE_ONLY: #FFEBEE (light red)
- WRITE_ONCE: #FFF3E0 (light orange)
- READ_WRITE_ONCE: #F3E5F5 (light purple)
- UNKNOWN: #F5F5F5 (light gray)

**Access Type Text:**
- READ_ONLY: "R"
- READ_WRITE: "RW"
- WRITE_ONLY: "W"
- WRITE_ONCE: "W1"
- READ_WRITE_ONCE: "RW1"
- UNKNOWN: "?"

**Confirmation Dialog:**
- Title: "Confirm Write to Critical Register"
- Icon: Warning icon
- Message: Shows register/field name, address, new value
- Warning text: "This is a critical peripheral. Writing incorrect values may cause device lockup or debug access loss." (red text)
- Checkbox: "Don't show this warning again"
- Buttons: OK (green), Cancel (default, red)

**Write Verification Dialog:**
- Title: "Write Verification Failed"
- Icon: Warning icon
- Message: "Written value: 0xX\nRead-back value: 0xY\n\nThis may be normal if register has read-only bits or hardware overrides."
- Button: OK

### DATA REQUIREMENTS

**AccessPolicy Class:**

## 9. OPERATION HISTORY

### USER REQUIREMENTS
- User sees chronological list of all read/write operations
- User can filter history by READ or WRITE operations
- User can select multiple operations to re-execute
- User can create actions from selected operations
- User can copy history to clipboard
- User can clear entire history
- User sees color-coded operations (blue for READ, green for WRITE)
- Auto-read operations do NOT appear in history (only manual reads)

### FUNCTIONAL REQUIREMENTS

**History Tracking:**
- Only manual operations logged (button clicks, not auto-reads)
- Each entry stores:
  - Timestamp (datetime.now())
  - Full register name
  - Operation type: 'read', 'write', 'field_write', 'prs'
  - Value (for writes)
  - Field name (for field writes) or None
- Stored in two parallel lists:
  - `history_items`: Raw data tuples
  - `all_items`: Display data tuples with color info

**Adding to History:**
- **Register Read**: `add_read_operation(full_name, value)`
  - Color: Light blue (220, 235, 255)
  - Format: "[HH:MM:SS] READ {full_name} → 0x{value:08X}"
- **Register Write**: `add_write_operation(full_name, value)`
  - Color: Light green (220, 255, 220)
  - Format: "[HH:MM:SS] WRITE {full_name} ← 0x{value:08X}"
- **Field Write**: `add_field_write_operation(full_name, field_name, value)`
  - Color: Light yellow (255, 255, 220)
  - Format: "[HH:MM:SS] WRITE {full_name}.{field_name} ← 0x{value:X} (full register: 0x{reg_value:08X})"
- **PRS Operation**: `add_prs_operation(description, register_ops)`
  - Color: Light purple (255, 230, 255)
  - Format: "[HH:MM:SS] PRS: {description}"

**Filtering:**
- Two checkboxes: READ (default: checked), WRITE (default: checked)
- On checkbox change: Rebuilds list based on checked states
- Filter applied to display only, raw history unchanged

**Re-execution:**
1. User selects one or more items (Ctrl/Shift+Click)
2. User clicks "▶ Run" button
3. For each selected item:
   - If READ: Reads register via `dut_interface.read_register()`
   - If WRITE: Writes register via `dut_interface.write_register()`
   - If PRS: Executes PRS register sequence
4. Emits `execute_history_item(full_name, operation, value)` signal per item
5. Main window updates displays after each execution

**Create Action from History:**
1. User selects one or more WRITE operations
2. User clicks "Create Action..." button
3. Filters selection to only WRITE operations (skips READS and PRS)
4. Shows warning if no write operations selected
5. Prompts for action name
6. Builds operations list:
   - For register writes: `{'register': full_name, 'value': value}`
   - For field writes: `{'register': reg_name, 'field': field_name, 'value': field_value}`
7. Emits `create_action(name, operations_list)` signal
8. Main window adds to actions panel

**Clear History:**
- User clicks "Clear" button
- Clears both `history_items` and `all_items` lists
- Clears list widget
- No confirmation (immediate action)

### UI REQUIREMENTS

**Panel Layout:**

- Append unit with space: "{value} {unit}"

**API Tree Population:**
1. Accesses `dut.dut_control` object
2. Enumerates API packages: Common, Host, LPW, WiFi
3. For each package: Lists modules (classes)
4. For each module: Lists methods
5. Deduplication:
   - Prefers classes over modules (class_module vs module)
   - Removes "_module" suffix for display
   - Skips private methods (starting with `_`)

- "RPC timeout" → Suggest `dut.rta.lpw.SetRpcTimeout(seconds)` or `ReInit()`

   - Remove button in Action column
5. Shows success popup: "Successfully routed {signal} to {pin} via PRS channel {channel}"

**Removing Route:**
1. User clicks "✖ Remove" button in table row
2. Calls `pti_prs.setup_prs(dut, pin, 'DISABLE', channel)`
3. Builds register operations list for history:
   - PRS.ASYNC_CH{channel}_CTRL.SOURCESEL = 0
   - PRS.ASYNC_CH{channel}_CTRL.SIGSEL = 0
   - GPIO.PRS0_ROUTEEN.ASYNCH{channel}PEN = 0
   - GPIO.PRS0_ASYNCH{channel}ROUTE.PORT = 0
   - GPIO.PRS0_ASYNCH{channel}ROUTE.PIN = 0
   - GPIO.PORT{X}_MODE{H/L}.MODE{pin_idx} = 0
4. Emits `prs_operation_performed(description, register_list)` signal
5. Removes row from table
6. Shows success popup
